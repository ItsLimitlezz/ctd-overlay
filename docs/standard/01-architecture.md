# 01 · Architecture

## 1.1 Layers

```
 ┌──────────── services ────────────┐
 │ Twitch  Kick  YouTube  Spotify OBS│   third parties
 └───┬──────┬─────┬───────┬──────┬───┘
     │      │     │       │      │      outbound: HTTPS, WebSocket, inbound webhooks
 ┌───▼──────▼─────▼───────▼──────▼───┐
 │            CONNECTORS             │   auth, polling, subscriptions, retries,
 │  normalize → events + state       │   rate limits, moderation, health
 └────────────────┬──────────────────┘
                  │
 ┌────────────────▼──────────────────┐
 │               BUS                  │   routing, state store, replay buffer,
 │   timeline scheduler · alert queue │   per-overlay filtering, clock
 └──────┬─────────────────────┬──────┘
        │ SSE / poll          │ SSE / REST
 ┌──────▼───────┐      ┌──────▼──────────────┐
 │   OVERLAYS   │      │ ADMIN UI · API      │
 │ template +   │      │ users, external     │
 │ runtime SDK  │      │ apps, Stream Deck   │
 └──────────────┘      └─────────────────────┘
   OBS browser sources
```

Data flows one way for display: **service → connector → bus → overlay → template**. Control
flows the other way: **admin/API → bus → connector** (e.g. "switch OBS to the BRB scene").

A template sits at the very end of the display flow and has no path back into connectors.

## 1.2 Components

### Core
The single server process. It **MUST** contain: HTTP server, authentication, storage, the
bus, the timeline scheduler, the connector host, the template registry, and the overlay
runtime host. It **MUST** run as one process with no required sidecar services.

### Connectors
One per service. Each implements the contract in [06-integrations.md](06-integrations.md):
it authenticates, keeps a live link to its service, emits normalized events and state, reports
health, and optionally exposes actions. A failing connector **MUST NOT** affect the core or
other connectors.

### Bus
Owns all live data. It **MUST**:
- hold current **state** as a key/value store (dotted keys, see 02);
- route **events** to subscribers filtered by what each overlay's template declared it consumes;
- keep a short **replay buffer** per overlay so a reconnecting client resumes without gaps
  (see §1.5);
- stamp every message with server time;
- run the **alert queue**: order, pace and time alerts per show, or per overlay outside a show
  (05 §5.5).

### Overlay runtime
Serves an overlay's page, injects the runtime SDK, delivers that overlay's data, manages scene
changes and animation lifecycle, shows queued alerts at the times the bus assigns, and hands the
template only what it declared.
Specified in [04-templates.md](04-templates.md) and [05-animation.md](05-animation.md).

### Admin UI
A web app served by the core. Specified in [08-admin-ui.md](08-admin-ui.md). It uses the same
public API as any external integration client — there is no private admin API.

## 1.3 The object model

```
Installation
 ├── Users ─────────────── roles: owner · admin · operator · viewer
 ├── Connections ───────── one per authorized service account
 ├── Templates ─────────── installed packages, versioned
 ├── Overlays ──────────── template + settings + bindings → permanent URL
 │     └── (optional) member of one Show
 ├── Shows ─────────────── overlays sharing scene state + one Timeline
 │     └── Timeline ── Cues
 ├── Media ─────────────── uploaded clips and images
 └── Webhooks ──────────── outbound subscriptions to other apps
```

- An **Overlay** pins one template version. Upgrading the template is an explicit action.
- An overlay **MAY** belong to at most one **Show**. Taking a scene on a show changes the scene
  of every member overlay together — this is how a horizontal and a vertical feed stay in
  lockstep. An overlay outside a show has its own scene.
- **Bindings** say which connections feed an overlay: e.g. a chat overlay bound to the Twitch,
  Kick and YouTube connections receives all three merged. Unbound data never reaches it. An
  overlay is bound to `"all"` connections (including ones made later) or to a list of them;
  `"all"` is the default, so an overlay shows a service's data as soon as it is connected.
  Changing the bindings reaches open pages at once (what an unbound connection showed goes),
  and never changes the URL.

## 1.4 Overlay URLs

```
https://<host>/o/<slug>?key=<overlay-key>[&canvas=<id> | &canvas=<w>x<h>]
```

- `slug` — human-readable, unique, chosen by the user (`friday-main`, `chat-vertical`).
- `key` — the overlay key (see 07). Required when the installation is in `public` exposure
  mode; **MAY** be waived per overlay in `local`/`lan` mode at the owner's choice.
- `canvas` — selects one of the template's declared canvases when it declares several, by its
  `id` (`canvas=v`, the form URLs generated by the platform use) or by its size
  (`canvas=1080x1920`). Anything else selects the default canvas. It is a property of the OBS
  source's size, not of the design, so it is the one allowed parameter.

**Permanence (hard rule).** The URL **MUST NOT** change when settings, bindings, the template
version, the active theme or the show membership change. The overlay re-renders in place. The
URL changes only when a user explicitly renames the slug or rotates the key, and the UI
**MUST** warn that OBS sources will need updating.

Development and preview **MAY** add override parameters (see 04 §4.9); production links
generated by the UI **MUST NOT** contain them.

## 1.5 Transport

### To our own clients: HTTP only
Overlays and the admin UI **MUST** be served live data over **Server-Sent Events**
(`text/event-stream`), with an HTTP polling fallback. The platform **MUST NOT** require
WebSocket between itself and its own clients.

Reasons, all observed in production: OBS's embedded browser handles plain HTTP reliably;
SSE reconnects automatically and resumes from `Last-Event-ID`; it passes every reverse proxy
and TLS terminator without upgrade configuration; and a dropped connection degrades to a
poll rather than to a dead source.

| Channel | Endpoint | Purpose |
|---|---|---|
| Snapshot | `GET /o/<slug>/snapshot` | Full current state for this overlay + a cursor |
| Stream | `GET /o/<slug>/stream` | SSE: events and state changes after the cursor |
| Poll | `GET /o/<slug>/poll?cursor=<c>` | Fallback: everything since the cursor, as JSON |

Client behaviour (implemented by the runtime SDK, not by templates):
1. Fetch the snapshot. Render.
2. Open the stream with `Last-Event-ID` = snapshot cursor.
3. Count the stream as **failed** when it errors, or when it hasn't opened within **5 s**. After
   two failures within 30 s, switch to polling every 700 ms (1500 ms in lite mode) and retry the
   stream every 60 s.

**Connection budget.** Over HTTP/1.1, Chromium-based browsers, OBS's included, keep at most six
connections open per host, shared by every page in the browser profile, and each open stream
holds one for good. With six streams open, *every* further request to the host waits in the
browser's queue: a seventh overlay's stream, its snapshot, its polls, even its page. Falling back
to polling doesn't help once the pool is full.

So over HTTP/1.1 the platform **MUST** hold at most **four** streams per client (remote address
plus `User-Agent`; behind a trusted proxy, the address it forwarded, 07 §7.8), which leaves two
connections for page loads, snapshots and polls. A stream request beyond that gets `429` with
problem type `https://skp.dev/errors/use-polling` and `Retry-After: 60`; the client polls at
once and retries the stream after that time. The 5 s open timeout in step 3 still covers a pool
that something else has filled. HTTP/2 (over TLS) multiplexes everything on one connection and
needs no cap. Implementations **SHOULD** be tested
with eight overlay sources in one OBS instance.

The server **MUST** keep each overlay's replay buffer for at least **120 seconds or 500
messages**, whichever is larger. If a cursor is older than the buffer, the server responds
`410 Gone` and the client re-fetches the snapshot.

SSE messages **MUST** carry `id:` (the cursor) and `event:` (the envelope `type`), and the
server **MUST** send a comment heartbeat (`: hb`) at least every 15 s so idle proxies don't cut
the connection.

### To third parties: whatever they require
Connectors open outbound WebSocket connections where a service demands it (obs-websocket,
Twitch EventSub WebSocket), call REST APIs, and receive inbound webhooks (Kick events). That
traffic never reaches a template.

## 1.6 Time

- The server clock is authoritative. Every envelope carries `ts` (server epoch milliseconds).
- The runtime estimates skew from snapshot and stream timestamps and exposes
  `SK.clock.now()` as server time. Countdowns, REC timers and synchronized animations
  **MUST** use it.
- One-shot visual triggers carry a server `startAt` and a duration; each client shows them
  for that window on server time. This keeps a horizontal and a vertical source on two
  different machines visually in sync.
- Show-time interpretation (the day boundary, time zones) is defined in
  [09-timeline.md](09-timeline.md).

## 1.7 Failure isolation

- A thrown error in any request handler, scheduler tick or connector **MUST** be caught,
  logged, and leave the process serving.
- A connector crash **MUST** restart that connector with exponential backoff (base 1 s,
  factor 2, cap 5 min, ±20 % jitter) without touching others.
- Overlays **MUST** keep rendering their last good state when the server is unreachable, and
  silently resume when it returns.
