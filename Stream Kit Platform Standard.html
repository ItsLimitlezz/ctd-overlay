Stream Kit Platform Standard · skp/1

Stream Kit Platform Standard (SKP) — v1.0 draft

Status: Draft · Date: 2026-10-09 · Identifier: skp/1

A specification for a self-hosted live-stream overlay platform: a server that connects to streaming platforms and OBS, normalizes everything into one data model, and serves styled overlays to OBS browser sources. It is written so that an independent implementation — and independent template authors — can build to it without reading anyone's source code.

It generalizes the D/PRTMNT Stream Kit (v0), which ran a live club night on this design. Every rule marked as a hard rule in 11-hard-rules.md was learned on air.

The one principle

Templates style. The platform connects.

A template never talks to Twitch, Kick, YouTube, Spotify or OBS. It never holds a token. It declares what data it wants and where things go on screen; the platform does the connecting, authenticating, normalizing, queueing, retrying and moderating. A chat template receives a merged, already-moderated stream of chat messages from every platform in one shape — and its whole job is to make them look good.

Everything else in this standard follows from that sentence.

Decisions this standard makes

These are settled. An implementation that departs from one is not SKP-conformant.

  1. Templates never connect. No template-originated network requests to third parties for data. Enforced with a Content Security Policy, not just convention. (04)
  2. Overlay URLs are permanent. Nothing configurable lives in an overlay URL — not the theme, not settings, not the template version. Changing any of it re-renders the sources already in OBS. Only an explicit key rotation changes a URL. (01, 11)
  3. HTTP to our own clients; no WebSocket. Overlays and the admin UI receive live data over Server-Sent Events with a polling fallback — plain HTTP that survives OBS's embedded browser, reverse proxies and flaky Wi-Fi. The platform does open WebSocket connections outward where a third party requires it (obs-websocket, Twitch EventSub). (01)
  4. The server owns the show. Scheduled cues fire on the server's clock. Closing every browser never stops a broadcast. (09)
  5. Bring your own platform credentials. Each installation registers its own Twitch, Kick, Google and Spotify developer apps. A self-hosted app cannot share one client ID: Spotify caps development-mode apps at a handful of users and gates extended access behind organization review, and every platform requires redirect URIs registered to your host. The admin UI walks the user through it. (06)
  6. Never show a wrong number. Missing or failed data hides; only real data renders. (02)
  7. Single tenant, multiple users. One installation serves one streamer or crew, with role-based accounts. Multi-tenant hosting is out of scope for v1.
  8. No native dependencies in the core. So it ships as a single executable on macOS and Linux and a small multi-arch image for TrueNAS. Media transcoding uses an external ffmpeg when present and is reported as unavailable when not. (10)

Non-goals for v1

  • A drag-and-drop canvas editor. Templates position their own elements and expose layout as settings. Composition happens in OBS by stacking overlay sources.
  • Streaming or encoding video. OBS does that.
  • Sending chat messages or moderating on platforms. Read-only for v1; the connector contract reserves capabilities for it.
  • Hosted multi-tenant SaaS.

Architecture

1.1 Layers

 │   timeline scheduler · alert queue │   per-overlay filtering, clock
 └──────┬─────────────────────┬──────┘
        │ SSE / poll          │ SSE / REST
 ┌──────▼───────┐      ┌──────▼──────────────┐

 └──────────────┘      └─────────────────────┘
   OBS browser sources

Data flows one way for display: service → connector → bus → overlay → template. Control flows the other way: admin/API → bus → connector (e.g. "switch OBS to the BRB scene").

A template sits at the very end of the display flow and has no path back into connectors.

1.2 Components

Core

The single server process. It MUST contain: HTTP server, authentication, storage, the bus, the timeline scheduler, the connector host, the template registry, and the overlay runtime host. It MUST run as one process with no required sidecar services.

Connectors

One per service. Each implements the contract in 06-integrations.md: it authenticates, keeps a live link to its service, emits normalized events and state, reports health, and optionally exposes actions. A failing connector MUST NOT affect the core or other connectors.

Bus

Owns all live data. It MUST:

  • hold current state as a key/value store (dotted keys, see 02);
  • route events to subscribers filtered by what each overlay's template declared it consumes;
  • keep a short replay buffer per overlay so a reconnecting client resumes without gaps (see §1.5);
  • stamp every message with server time.

Overlay runtime

Serves an overlay's page, injects the runtime SDK, delivers that overlay's data, manages scene changes, alert queues and animation lifecycle, and hands the template only what it declared. Specified in 04-templates.md and 05-animation.md.

Admin UI

A web app served by the core. Specified in 08-admin-ui.md. It uses the same public API as any external integration client — there is no private admin API.

1.3 The object model

Installation
 ├── Users ─────────────── roles: owner · admin · operator · viewer
 ├── Connections ───────── one per authorized service account
 ├── Templates ─────────── installed packages, versioned
 ├── Overlays ──────────── template + settings + bindings → permanent URL
 │     └── (optional) member of one Show
 ├── Shows ─────────────── overlays sharing scene state + one Timeline
 │     └── Timeline ── Cues
 ├── Media ─────────────── uploaded clips and images
 └── Webhooks ──────────── outbound subscriptions to other apps
  • An Overlay pins one template version. Upgrading the template is an explicit action.
  • An overlay MAY belong to at most one Show. Taking a scene on a show changes the scene of every member overlay together — this is how a horizontal and a vertical feed stay in lockstep. An overlay outside a show has its own scene.
  • Bindings say which connections feed an overlay: e.g. a chat overlay bound to the Twitch, Kick and YouTube connections receives all three merged. Unbound data never reaches it.

1.4 Overlay URLs

https://<host>/o/<slug>?key=<overlay-key>[&canvas=<w>x<h>]
  • slug — human-readable, unique, chosen by the user (friday-main, chat-vertical).
  • key — the overlay key (see 07). Required when the installation is in public exposure mode; MAY be waived per overlay in local/lan mode at the owner's choice.
  • canvas — selects one of the template's declared canvases when it declares several. It is a property of the OBS source's size, not of the design, so it is the one allowed parameter.

Permanence (hard rule). The URL MUST NOT change when settings, bindings, the template version, the active theme or the show membership change. The overlay re-renders in place. The URL changes only when a user explicitly renames the slug or rotates the key, and the UI MUST warn that OBS sources will need updating.

Development and preview MAY add override parameters (see 04 §4.9); production links generated by the UI MUST NOT contain them.

1.5 Transport

To our own clients: HTTP only

Overlays and the admin UI MUST be served live data over Server-Sent Events (text/event-stream), with an HTTP polling fallback. The platform MUST NOT require WebSocket between itself and its own clients.

Reasons, all observed in production: OBS's embedded browser handles plain HTTP reliably; SSE reconnects automatically and resumes from Last-Event-ID; it passes every reverse proxy and TLS terminator without upgrade configuration; and a dropped connection degrades to a poll rather than to a dead source.

ChannelEndpointPurpose
SnapshotGET /o/<slug>/snapshotFull current state for this overlay + a cursor
StreamGET /o/<slug>/streamSSE: events and state changes after the cursor
PollGET /o/<slug>/poll?cursor=<c>Fallback: everything since the cursor, as JSON

Client behaviour (implemented by the runtime SDK, not by templates):

  1. Fetch the snapshot. Render.
  2. Open the stream with Last-Event-ID = snapshot cursor.
  3. If the stream fails twice within 30 s, switch to polling every 700 ms (1500 ms in lite mode) and retry the stream every 60 s.

The server MUST keep each overlay's replay buffer for at least 120 seconds or 500 messages, whichever is larger. If a cursor is older than the buffer, the server responds 410 Gone and the client re-fetches the snapshot.

SSE messages MUST carry id: (the cursor) and event: (the envelope type), and the server MUST send a comment heartbeat (: hb) at least every 15 s so idle proxies don't cut the connection.

To third parties: whatever they require

Connectors open outbound WebSocket connections where a service demands it (obs-websocket, Twitch EventSub WebSocket), call REST APIs, and receive inbound webhooks (Kick events). That traffic never reaches a template.

1.6 Time

  • The server clock is authoritative. Every envelope carries ts (server epoch milliseconds).
  • The runtime estimates skew from snapshot and stream timestamps and exposes SK.clock.now() as server time. Countdowns, REC timers and synchronized animations MUST use it.
  • One-shot visual triggers carry a server startAt and a duration; each client shows them for that window on server time. This keeps a horizontal and a vertical source on two different machines visually in sync.
  • Show-time interpretation (the day boundary, time zones) is defined in 09-timeline.md.

1.7 Failure isolation

  • A thrown error in any request handler, scheduler tick or connector MUST be caught, logged, and leave the process serving.
  • A connector crash MUST restart that connector with exponential backoff (base 1 s, factor 2, cap 5 min, ±20 % jitter) without touching others.
  • Overlays MUST keep rendering their last good state when the server is unreachable, and silently resume when it returns.

Every piece of live data in the platform is either an event or state, wrapped in one envelope. Connectors produce them, templates and external apps consume them, and none of them need to know which service a value came from unless they want to.

2.3 Chat

Chat is the most demanding stream, so the platform does the heavy lifting: it merges platforms, parses emotes into fragments, applies deletions and bans, and keeps a rolling buffer so a template that loads mid-stream isn't empty.

chat.message

json
{
  "id": "msg_01J9Z6…",
  "platformMessageId": "b6c1e…",
  "channel": "dprtmnt",
  "user": {
    "id": "twitch:12345",
    "login": "trapment",
    "name": "Trapment",
    "color": "#16E0FF",
    "avatar": "https://…/profile_image.png",
    "roles": ["subscriber", "vip"],
    "badges": [ { "id": "subscriber/12", "label": "12-month subscriber", "image": "https://…" } ]
  },
  "text": "that drop 🔥 PogChamp",

    { "type": "text",  "text": "that drop 🔥 " },

  • user.id MUST be prefixed with the platform (twitch:, kick:, youtube:) so IDs never collide across platforms.
  • roles is normalized across platforms to this closed set: broadcaster, moderator, vip, subscriber, member, verified, founder, artist, bot. A template styles roles, not platform-specific badge IDs.
  • fragments types: text, emote, mention, link, cheermote. Concatenating every fragment's text MUST reproduce text.
  • color MAY be absent (YouTube has none). Templates MUST handle that.
  • Third-party emote sets (7TV, BTTV, FFZ) MAY be resolved by an optional connector into emote fragments; templates see no difference.

{ "messageId": "msg_01J9Z6…" } — the template MUST remove it from screen. The runtime also removes it from its buffer and from any not-yet-rendered queue.

chat.user.cleared

{ "userId": "twitch:12345" } — a ban or timeout: remove all of that user's messages.

chat.cleared

{} — the channel's chat was cleared: remove everything.

Chat buffer in the snapshot

The snapshot MUST include chat.recent: the last N messages (N declared by the template, default 50, max 200) that are still visible after moderation, oldest first.

2.7 Custom types

External apps and connectors outside this standard MUST use one of:

  • custom.<name> — installation-local, ad hoc;
  • x-<vendor>.<name> — published by a third-party integration (x-streamdeck.button).

State keys follow the same rule: custom.* or x-<vendor>.*. Unprefixed types and keys are reserved for this standard. The platform MUST reject unprefixed custom publishes with 422.

2.8 Absence, staleness and zero

This is a hard rule (11 §H6). For any value displayed on air:

  • Unknown → the key is absent. Templates hide the element.
  • Real zero → 0. Only when a service authoritatively reported zero (e.g. a channel that is verifiably offline).
  • Error → hold the last good value for up to 120 s with <key>.stale = true, then remove the key.

A connector MUST NOT publish 0 because a request failed.

2.9 Size and rate limits

  • An envelope MUST NOT exceed 64 KiB serialized. Chat messages longer than 1000 characters are truncated by the connector with "truncated": true.
  • The bus MUST coalesce state.changed for the same key to at most 10 per second per overlay.
  • If an overlay's outbound queue exceeds 1000 envelopes, the platform drops the oldest chat.message events first and sets chat.dropped in the next envelope's metadata.

04

Templates

A template is a design. It decides how things look, where they sit and how they move. It does not decide where data comes from — that is the platform's job (README, "The one principle").

A template can be as large as a whole show package (countdown, BRB, timetable, intros) or as small as a single chat box. Users compose several in OBS by stacking overlay sources.

4.1 Package format

A template is a ZIP archive with the extension .skp:

vikkstar-event/
├── template.json        manifest (REQUIRED)
├── index.html           entry document (REQUIRED, path configurable)
├── template.css
├── template.js
├── assets/              images, fonts, video, Lottie JSON
├── previews/            screenshots shown in the gallery (REQUIRED: at least one)
└── LICENSE
  • Total size MUST NOT exceed 100 MiB; a single file 50 MiB.
  • Paths are relative, lowercase recommended, no .., no absolute paths, no symlinks. The platform MUST reject archives violating this (zip-slip protection).
  • Everything the template loads at runtime MUST be inside the package, except the images the data itself points to (avatars, emotes, album art) and fonts from allowed hosts (§4.8).

Field rules

  • id — reverse-DNS, globally unique, immutable for the life of the template.
  • version — SemVer. A major bump means existing overlays' settings may not migrate automatically (§4.10).
  • category — one of show (multi-scene package), chat, alerts, now-playing, lower-third, background, ticker, goal, scoreboard, widget.
  • scenes[].core — maps the scene to a core scene so shows, timelines and buttons work across templates: auto, starting, program, brb, lineup, outro, bg, intro. A scene without core is a template extra (e.g. headliner). A show-category template MUST provide starting, program, brb and outro; it SHOULD provide all eight.
  • scenes[].then + durationMs — a timed scene that returns automatically. The server performs the return (09 §9.3), so it happens even if no browser is watching.
  • consumes — least privilege. The runtime delivers only matching state keys and event types; everything else never leaves the server. Wildcards: alert.*, show.*.
  • chat.recent — how many buffered messages the snapshot includes (0–200). chat.max — the most messages the template keeps on screen; the runtime unmounts older ones (05 §5.6).

4.4 Runtime SDK

The runtime injects /sdk/v1/sk.js before the template's scripts and exposes a frozen global SK. Templates MUST obtain all live data through it.

js
SK.ready(() => { /* snapshot loaded, settings resolved, safe to render */ });

// settings
SK.settings                       // resolved values (defaults applied)
SK.onSettings(s => restyle(s))    // live edits from the admin UI

// state
SK.state('viewers.total')         // current value or undefined
SK.onState('viewers.total', (v, prev) => …)   // also fires once on ready
SK.onState('show.*', (key, v) => …)

// events
SK.on('alert.*', e => …)          // only types declared in consumes
SK.on('show.trigger', e => …)

// scenes
SK.scene                          // current scene id
SK.onScene((scene, prev, transition) => …)

// actions this template declared
SK.action('titleCard', ({ args, startAt, durationMs }) => showCard(args))

// chat helper (merged, moderated, buffered)
SK.chat.recent()                  // array, oldest first
SK.chat.onAdd(m => …); SK.chat.onRemove(id => …); SK.chat.onClear(() => …)

// music helper
SK.music.track()                  // Track or undefined
SK.music.progress()               // interpolated ms

// alerts: the runtime queues; the template renders one at a time
SK.alerts.render(async (alert, el) => { … resolves when exit animation is done … })

// animation lifecycle (see 05)
SK.mount(el, { enter: 'rise', durationMs: 600 })
SK.unmount(el)                    // resolves after the exit animation

// time & environment
SK.clock.now()                    // server time
SK.clock.at(ts, fn)               // run fn at a server time
SK.canvas                         // { id, width, height }
SK.env                            // { preview, lite, reducedMotion, obs }
SK.asset('assets/poster-h.jpg')   // versioned, cacheable URL
SK.log.warn('…')                  // forwarded to the platform's template log

The SDK MUST be dependency-free, under 25 KB gzipped, and run in the browser engine of the oldest OBS version the platform supports (10 §10.2).

4.5 Rendering contract

  • The runtime sets <html data-skp-canvas="h" data-skp-scene="program"> and scales a fixed stage of the canvas size to the viewport. Templates lay out in canvas pixels and never compute scaling themselves.
  • The page background MUST be transparent unless the active scene declares otherwise. OBS composites the overlay over the camera.
  • A template MUST render something sensible with empty data: before the snapshot, with no connections bound, and with every optional key absent.
  • A template MUST NOT depend on requestAnimationFrame for correctness. Use timers, CSS animations or SK.clock.at (05 §5.7).

4.6 Actions

Actions are named moments a template can perform: a title card, a now-playing lower third, a schedule chip, a goal celebration. Declaring them in the manifest makes them appear as buttons in the admin UI, as cue actions on the timeline, and as POST /overlays/{id}/actions/{name} — with no extra work.

The runtime calls the registered handler with { args, startAt, durationMs }. The template shows the element from startAt for durationMs on server time, then hides it. A trigger that arrives after its window has passed MUST NOT be shown.

4.7 Scenes and transitions

The runtime owns scene switching: it mounts the incoming scene container (<section data-skp-scene-root="brb">), runs the outgoing scene's exit and the incoming scene's enter (05 §5.4), then removes the old container. A template provides each scene's markup by either:

  • declarative — <template data-skp-scene="brb">…</template> blocks in index.html; or
  • imperative — SK.defineScene('brb', ctx => element).

4.8 Sandbox and Content Security Policy

Templates are third-party code running inside OBS and inside the admin UI's preview. The platform MUST serve overlay pages with:

Content-Security-Policy:
  default-src 'none';
  script-src 'self';
  style-src 'self' 'unsafe-inline' https://fonts.googleapis.com;
  font-src 'self' https://fonts.gstatic.com data:;
  img-src 'self' data: https:;
  media-src 'self' blob:;
  connect-src 'self';
  frame-ancestors 'self';
  base-uri 'none';
  form-action 'none'

connect-src 'self' is what makes "templates never connect" enforceable: a template cannot fetch from a third party even if it tries. img-src https: exists because avatars, emotes and album art legitimately come from platform CDNs. Additional font hosts MAY be allowed only if listed in fonts.

In the admin UI, previews MUST load in <iframe sandbox="allow-scripts"> — without allow-same-origin — so a template can never read the operator's session or the admin DOM. Overlay endpoints authorize by key, not cookie, and answer GET with Access-Control-Allow-Origin: *, which is what lets the opaque-origin preview still stream data.

A template MUST NOT receive tokens, credentials, other overlays' data, or any state key it did not declare.

4.9 Preview overrides

For development and the admin UI only, the overlay URL accepts: ?scene=<id> (force a scene), ?bg=dark (opaque backdrop), ?lite=1 (drop GPU-heavy layers — mobile previews), ?mock=1 (sample data, 08 §8.5), ?debug=1 (diagnostic HUD), ?settings=<base64> (unsaved settings being edited). URLs generated for OBS MUST NOT include them.

4.10 Versioning and migration

  • Overlays pin id@version. Installing a newer version never changes running overlays.
  • POST /overlays/{id}/upgrade migrates settings: unchanged keys copy over, removed keys drop, new keys take defaults. A template MAY ship migrate.js exporting migrate(fromVersion, settings) → settings for renames; it runs server-side in an isolated context with no I/O.
  • Across a major version the UI MUST show what will change before upgrading.

4.11 Validation

POST /templates/validate (and the same check on install) MUST verify: manifest against the schema; standard is supported; every referenced file exists; previews exist; no path escapes; scene and action IDs unique; show templates provide the required core scenes; the entry renders without throwing under ?mock=1 in a headless check when available. Errors block install; warnings (e.g. a missing bg scene) are shown.

05

Animation

Animation is where templates spend their effort, so the platform gives them a small, strict contract: a lifecycle for every element, a scheduler that is synchronized to server time, and queues for things that arrive in bursts. Templates write the motion; the runtime decides when.

5.1 Engines

Templates MAY animate with any of:

EngineUseNotes
CSS transitions & keyframesDefault for everythingCheapest; survive tab throttling
Web Animations APISequenced, seekable motionelement.animate(); seekable in previews
LottieDesigner-made vector animationBundle the player in the package; no CDN
Video (WebM VP9 with alpha)Stingers, complex introsPlays muted; audio belongs in OBS
Canvas 2D / WebGLParticles, generative backgroundsBudget carefully (§5.8)

All animation MUST be self-contained in the package.

5.2 Element lifecycle

Every element the runtime shows or hides moves through four states, exposed as an attribute so CSS can target them:

  (absent) ──mount──► enter ──► idle ──unmount──► exit ──► (removed)
css
.card[data-skp-state="enter"] { animation: rise .6s cubic-bezier(.2,.7,.2,1) both; }
.card[data-skp-state="idle"]  { animation: breathe 4s ease-in-out infinite; }
.card[data-skp-state="exit"]  { animation: drop .45s ease-in both; }
  • SK.mount(el, opts) inserts the element with data-skp-state="enter", then switches to idle after the enter duration.
  • SK.unmount(el) sets exit and removes the element after the exit duration. It returns a promise.
  • Duration is resolved in order: opts.durationMs → CSS custom property --skp-enter-ms / --skp-exit-ms → the computed animation duration → 0.
  • The runtime MUST NOT wait on animationend alone. It uses the resolved duration plus 50 ms as a deadline, because animationend does not fire on elements that are hidden or in a throttled source. (Hard rule 11 §H9.)

5.3 Synchronized timing

Two sources on two machines — a horizontal and a vertical feed — must hit the same beat.

  • Every trigger carries startAt in server time (02 §2.6). The runtime begins the element's enter at startAt on SK.clock.now(), not on receipt.
  • If a trigger arrives late but inside its window, the runtime SHOULD start it immediately and offset WAAPI/CSS animations by the lateness (animation-delay: -Xms) so it lands on the same final frame as on-time clients.
  • If the window has passed, it is dropped.
  • SK.clock.at(ts, fn) schedules a callback against server time; it re-checks on a 250 ms timer, so it stays correct across clock corrections and throttled tabs.

5.4 Scene transitions

On a scene change the runtime:

  1. mounts the incoming scene root in enter;
  2. sets the outgoing root to exit;
  3. removes the outgoing root after its exit duration.

Both overlap by default (crossfade). A template controls the look entirely in CSS:

css
[data-skp-scene-root][data-skp-state="enter"] { animation: sceneIn .5s ease both; }
[data-skp-scene-root][data-skp-state="exit"]  { animation: sceneOut .5s ease both; }

The transition name requested by the operator (cut, fade, stinger, or a template-defined name) is exposed as data-skp-transition on both roots. cut MUST skip animations entirely. A template MAY declare a stinger:

json
"transitions": [ { "id": "stinger", "media": "assets/stinger.webm", "cutAtMs": 420 } ]

The runtime plays the video over both scenes and swaps them at cutAtMs.

5.5 Alert queue

Alerts arrive in bursts (a gift of 50 subs is 51 events). The runtime — not the template — queues them per overlay according to the manifest:

alerts fieldMeaningDefault
modeserial (one at a time) or stack (several visible)serial
maxConcurrentfor stack3
minDisplayMsminimum time on screen4000
gapMspause between alerts500
maxQueuealerts held before the oldest low-priority ones are dropped50
coalescemerge a gift burst into one alert.gift with the totaltrue

Priority, highest first: raid, superchat/tip, gift, subscription, membership, cheer/kicks, follow. The operator can pause, skip and replay alerts from the admin UI.

The template supplies only the renderer:

js
SK.alerts.render(async (alert, el) => {
  el.innerHTML = `<b>${alert.user.name}</b> ${verb(alert)}`;
  await SK.mount(el, { durationMs: 600 });
  await wait(Math.max(SK.settings.alertHoldMs, 4000));
  await SK.unmount(el);
});

5.6 Chat animation

The chat helper handles pacing: when messages arrive faster than a template can animate, the runtime batches them into frames of at most 4 messages per 250 ms and caps on-screen messages at the template's chat.max (default 30), unmounting the oldest with their exit animation. Deleted messages unmount immediately with their exit animation; a chat.cleared exits everything at once.

5.7 Timers versus animation frames

requestAnimationFrame MUST NOT gate correctness. OBS can stop delivering frames to a source that isn't currently painting, and a browser preview tab in the background is throttled to roughly one timer per second. Use CSS or WAAPI for motion (the compositor keeps running) and timers or SK.clock.at for state. requestAnimationFrame is fine for canvas drawing loops whose pause is harmless.

5.8 Performance budget

One OBS scene often holds four or more overlay sources, each its own browser.

  • Animate transform and opacity only. Never animate width, height, top, left, box-shadow or filter: blur() in loops.
  • Do not use backdrop-filter to blur the camera: a browser source only sees its own page, so it blurs nothing useful and costs GPU. Darken with a translucent fill; blur the camera with an OBS filter.
  • Do not use mix-blend-mode on transparent overlays. With nothing beneath it inside the page, multiply composites to black and covers the camera.
  • At most two infinite animations per scene in idle; prefer steps() for texture loops.
  • Canvas/WebGL: cap at 30 fps unless the effect needs 60; stop the loop when its scene exits.
  • Large images: decode ahead (img.decode()) before the first animated reveal, or the first showing stutters.
  • Lite mode (SK.env.lite): the runtime adds data-skp-lite to <html>; templates SHOULD drop blurs, grain, particles and video under it. Mobile previews use it so several overlay iframes don't exhaust a phone's GPU memory.

5.9 Reduced motion and previews

  • In the admin UI only, the runtime honours prefers-reduced-motion by setting data-skp-reduced-motion; templates SHOULD shorten or skip motion under it. On air, OBS sources always animate.
  • Preview scrubbing: the admin UI MAY pause and seek a template by setting currentTime on every animation from document.getAnimations(). Templates that use CSS or WAAPI get this for free; canvas loops should read SK.clock.now() rather than wall time to stay scrubbable.

Integrations

The platform does all connecting. This document defines the contract every connector meets, then the specifics for each service in v1, then how other apps plug in.

Verified 2026-10-09. Platform APIs change. Each service section lists what was confirmed against official documentation or developer announcements on that date. Implementers MUST re-check scopes, endpoints and limits against the linked sources before release and update this file.

6.1 Connector contract

ts
interface Connector {
  id: string                         // "twitch"
  name: string                       // "Twitch"
  capabilities: Capability[]         // see 6.2
  credentials: CredentialSpec        // what the user must supply (client ID, secret, password…)
  auth: 'oauth-pkce' | 'oauth-code' | 'device-code' | 'client-credentials'
      | 'password' | 'none'
  requiresPublicUrl?: boolean        // true if the service pushes to us (webhooks)

  start(ctx: ConnectorContext): Promise<void>
  stop(): Promise<void>
  health(): Health                    // see 6.3
  actions?: Record<string, ActionSpec>
}

interface ConnectorContext {
  connection: Connection              // decrypted credentials + tokens, in memory only
  publish(envelope: EnvelopeInput): void       // events
  setState(key: string, value: unknown): void   // state; undefined = remove
  saveTokens(tokens: TokenSet): Promise<void>  // persisted encrypted
  http: HttpClient                    // timeouts, retries, 429 handling built in
  log: Logger                         // redacts secrets
  publicUrl?: string                  // SKP_PUBLIC_URL, when set
  schedule(ms: number, fn: () => void): Cancel
}

A connector MUST:

  • never block the event loop or throw out of start; failures become health.status = "error";
  • refresh tokens before expiry (at 80 % of lifetime) and once more on any 401, then stop and report needs-reauth rather than retrying in a loop;
  • honour 429 and Retry-After; back off exponentially with jitter on 5xx and network errors (base 1 s, ×2, cap 5 min);
  • stop calling a service whose quota is exhausted until the documented reset, and say so in health.detail;
  • publish only normalized types (02) — never raw service payloads;
  • follow the absence rules (02 §2.8): never publish 0 for a failure;
  • deduplicate pushed events by the service's message ID for at least 10 minutes;
  • keep credentials and tokens in memory only via ctx.connection, never in logs or envelopes.

6.5 Twitch

Auth: Device Code Flow (generally available; supports public and confidential app types), falling back to Authorization Code. One user token from the broadcaster's account serves an installed app — no separate bot account. App token (client credentials) for public reads.

Chat — EventSub over WebSocket.

  • Connect to the EventSub WebSocket endpoint; on the welcome message, create subscriptions using its session ID before the documented deadline; handle session_keepalive, session_reconnect (connect to the new URL before closing the old) and revocations.
  • channel.chat.message with condition broadcaster_user_id + user_id, where user_id MUST be the account that owns the token (mismatches return 403). Scope: user:read:chat (formerly chat:read). Bot scopes (user:bot, channel:bot) are only needed for webhook or Conduit transports, which v1 does not use.
  • Moderation: channel.chat.message_delete → chat.message.deleted; channel.chat.clear_user_messages → chat.user.cleared; channel.chat.clear → chat.cleared.
  • channel.chat.notification carries subs, resubs, gift bombs, raids and announcements as they appear in chat; map to alert.* where the dedicated subscription isn't used, and dedupe against it.
  • Emotes arrive as fragments with IDs; resolve to the emote CDN. Badges resolve via the global and channel chat-badge endpoints, cached for 24 h.

Alerts: channel.follow (v2, moderator:read:followers), channel.subscribe, channel.subscription.gift, channel.subscription.message (channel:read:subscriptions), channel.cheer (bits:read), channel.raid.

Viewers & status: GET /helix/streams?user_login=<login> → data[0].viewer_count; an empty data array means offline (authoritative zero). stream.online / stream.offline via EventSub update stream.twitch.live instantly.

Sources: dev.twitch.tv/docs/eventsub, dev.twitch.tv/docs/chat/authenticating, dev.twitch.tv/docs/authentication/getting-tokens-oauth.

6.6 Kick

Auth: OAuth 2.1 with PKCE for the broadcaster's user token; client credentials for public reads. The broadcaster must authorize the installation's app before any of their events flow.

Viewers & status: GET https://api.kick.com/public/v1/channels?slug=<slug> with Authorization: Bearer <token> → data[0].stream.viewer_count and stream.is_live.

Chat and alerts — webhooks only. Kick's public API delivers events (chat.message.sent, follows, subscriptions, gifts, kicks, livestream status) exclusively by webhook: the installation subscribes via POST /public/v1/events/subscriptions (scope events:subscribe) and Kick POSTs each event to a public HTTPS URL. Consequences the platform MUST handle:

  • A public URL is required. In local or lan exposure mode (07 §7.8), the Kick connector runs degraded: viewer count and live status work; chat and alerts are unavailable, and the UI says exactly that and how to fix it (public mode, or a tunnel that provides HTTPS).
  • Verify every delivery. Check the signature header against Kick's public key (fetched from /public/v1/public-key, cached, refetched on verification failure), require a fresh timestamp (±5 min), and dedupe on the message ID.
  • Re-subscribe defensively. Kick removes subscriptions whose endpoint fails for about a day. On startup and every 6 hours, list subscriptions and recreate missing ones.
  • Expect gaps. Developers have reported stalled chat delivery. Health MUST turn degraded when no chat event has arrived for 10 minutes while the channel is live.

An unofficial Pusher-based chat feed exists and works without a public URL. It is not part of Kick's public API. A connector MAY offer it only as an explicit opt-in labelled "Unofficial — may break without notice", never as the default.

Viewer-count caveat: when a streamer hides their viewer count, the official API reports 0 while unofficial sources report the real number. The platform uses the official value.

Sources: docs.kick.com, github.com/KickEngineering/KickDevDocs (webhook security, events).

6.7 YouTube

Auth: Google OAuth (Authorization Code + PKCE), scope youtube.readonly, with the user's own Google Cloud project.

Quota is the constraint. The YouTube Data API grants 10,000 units per day by default, resetting at midnight Pacific time. Every request — including failed ones — costs at least one unit. The connector MUST:

  • keep a running unit estimate and expose it in health.quota;
  • on quotaExceeded, stop all YouTube calls until the reset and set health to degraded with the reset time. Treating it as a rate limit and retrying has burned entire days of quota in real deployments;
  • let the owner set a daily budget below the quota, leaving headroom for other tools.

Finding the chat: liveBroadcasts.list (broadcastStatus=active, mine=true) → snippet.liveChatId. Re-check every 5 minutes while not live; stop when live.

Chat: prefer liveChatMessages.streamList — a server-streaming connection Google recommends for low latency and quota efficiency. Fall back to liveChatMessages.list, honouring the returned pollingIntervalMillis and nextPageToken exactly; never poll faster. The quota cost of streamList was not documented at verification time; measure it in the Cloud Console before release and record it here.

Alerts arrive as chat items by snippet.type: superChatEvent, superStickerEvent → alert.superchat; newSponsorEvent, memberMilestoneChatEvent → alert.membership.

6.8 Spotify

Auth: Authorization Code + PKCE, scopes user-read-currently-playing and user-read-playback-state. Register the redirect URI exactly; for a desktop install use a loopback IP redirect (http://127.0.0.1:<port>/oauth/callback/spotify) — confirm Spotify's current redirect rules at implementation.

Every installer brings their own app, and must have Premium. Since February 2026, Spotify development-mode apps require the app owner to hold an active Spotify Premium subscription and are limited to a small number of users; extended access is restricted to organizations meeting review criteria. A self-hosted platform therefore cannot ship a shared client ID. The setup guide MUST say so plainly, before the user starts.

Now playing: GET https://api.spotify.com/v1/me/player/currently-playing — 200 with item, or 204 when nothing is playing (key music.nowPlaying removed). Poll every 3 s while playing, every 15 s while paused or idle; on 429 wait Retry-After. Use progress_ms with the response timestamp to fill progressMs / progressAt; the runtime interpolates.

Other music sources: anything that can PUT /api/v1/state/custom.music (a desktop helper, a DJ-software bridge) can feed a now-playing template. A connector MAY map such a source to music.nowPlaying so music templates work unchanged.

Sources: developer.spotify.com/documentation/web-api, the February 2026 migration guide, and the April 2025 extended-access criteria announcement.

6.9 OBS Studio

OBS has no webhooks; integration is through obs-websocket, built into OBS Studio since 28. The platform connects as a client to OBS, which listens on port 4455 by default (configurable in OBS under Tools → WebSocket Server Settings).

Handshake (protocol v5):

  1. Server sends Hello (op 0) with authentication.challenge and authentication.salt when a password is set.
  2. Client computes secret = base64(sha256(password + salt)), then auth = base64(sha256(secret + challenge)).
  3. Client sends Identify (op 1) with rpcVersion, authentication and eventSubscriptions (a bitmask; use the All value of the protocol version being targeted — it grew when the Canvases category was added, so don't hardcode a number).
  4. Server replies Identified (op 2). Then: Request (6) / RequestResponse (7), Event (5), RequestBatch (8) / RequestBatchResponse (9), Reidentify (3).

State: obs.scene from GetCurrentProgramScene and the CurrentProgramSceneChanged event; obs.streaming from GetStreamStatus / StreamStateChanged; obs.recording from RecordStateChanged.

Actions: obs.setScene (SetCurrentProgramScene), obs.listScenes (GetSceneList), obs.toggleSource, and obs.addOverlay — creates a browser source for an overlay via CreateInput with the overlay URL and the canvas width/height, so "Add to OBS" is one click.

Scene mapping. An overlay or show MAY map OBS scenes to overlay scenes ("BRB" → brb, "Live" → program). When OBS changes scene, the platform takes the mapped overlay scene — the operator switches once, in OBS, and the graphics follow. Timeline cues MAY do the reverse with obs.setScene.

Placement and security. OBS usually runs on the streaming PC while the platform runs on a NAS, so the connection is LAN-to-LAN. A password is REQUIRED. obs-websocket MUST NOT be port-forwarded to the internet; the UI warns if the configured host is not a private address. Reconnect with backoff when OBS closes — it restarts often.

Sources: github.com/obsproject/obs-websocket — docs/generated/protocol.md.

7.2 First-run setup

There are no default credentials, ever.

  • On first start with no owner account, the platform prints a one-time setup code to its log (and, on desktop, shows it in the app window).
  • POST /api/v1/setup requires that code and creates the owner. The code expires after 1 hour or first use; a restart issues a new one.
  • In public exposure mode the setup endpoint MUST additionally refuse requests that do not come from a loopback or private address, so an exposed fresh install cannot be claimed by a stranger who finds it first.

7.3 Passwords and sessions

Hashing. Passwords MUST be hashed with a memory-hard KDF:

  • scrypt — N = 2¹⁷, r = 8, p = 1, 16-byte random salt, 32-byte output (available in the Node.js standard library, keeping the core dependency-free); or
  • Argon2id — m = 19 MiB, t = 2, p = 1, where a native implementation is acceptable.

Store alg$params$salt$hash so parameters can be raised later; rehash on next login when they change. Minimum length 12, maximum 256; check against a bundled list of common passwords; no composition rules.

Sessions.

  • Session IDs: 256 bits from a CSPRNG. Store only their SHA-256 server-side.
  • Cookie: HttpOnly, SameSite=Lax, Path=/. Over HTTPS: Secure and the __Host- name prefix (__Host-skp_session). Over plain HTTP on a LAN: skp_session without Secure.
  • Idle timeout 12 h; absolute lifetime 30 days ("keep me signed in") or 24 h otherwise.
  • Rotate the session ID on login and on any privilege change. Invalidate all of a user's sessions on password change, 2FA change or role change.
  • Users can see and revoke their active sessions (device, IP, last seen).

CSRF. State-changing requests (POST, PUT, PATCH, DELETE) authenticated by cookie MUST carry X-SKP-CSRF equal to the session's CSRF token (from GET /auth/session), and the Origin header, when present, MUST match the platform's origin. Token-authenticated requests are exempt.

Login protection. 10 failed attempts per account or per IP within 15 minutes triggers an exponential delay (1 s → 2 s → … → 15 min). Error messages never reveal whether the account exists. Failed and successful logins go to the audit log.

7.4 Two-factor authentication

TOTP (RFC 6238, SHA-1, 6 digits, 30 s, ±1 step) with 10 single-use recovery codes stored hashed. In public mode 2FA SHOULD be required for owner and admin roles and the UI nags until it is enabled. WebAuthn passkeys MAY be supported in addition.

7.6 Overlay keys

OBS browser sources can't log in, so overlays use capability URLs.

  • skp_ovl_ + 24 random bytes, one per overlay.
  • Grants read access to that overlay's page, assets, snapshot and stream — nothing else.
  • Stored encrypted (not hashed), because the UI must be able to show the URL again for copying.
  • Rotating it is explicit and warns that OBS sources must be updated.
  • Overlay responses send Referrer-Policy: no-referrer; the platform MUST redact key= values from access logs and error reports.
  • In local/lan mode the owner MAY mark an overlay "no key required".

7.7 Secrets at rest

All third-party credentials, OAuth tokens, overlay keys and webhook secrets MUST be encrypted with AES-256-GCM (random 96-bit nonce per record, record ID as associated data).

  • The 32-byte master key comes from SKP_MASTER_KEY (base64) or SKP_MASTER_KEY_FILE.
  • If neither is set on first start, the platform generates one into the config directory with 0600 permissions — deliberately outside the data directory — and warns that backing up data without the key makes secrets unrecoverable.
  • Ciphertexts carry a key ID so the key can be rotated (skp key rotate re-encrypts in place).
  • Decrypted secrets live only in connector memory.

7.11 Input, uploads and processing

  • Validate every request body against its schema; reject unknown fields on writes.
  • Resolve every filesystem path and confirm it stays inside its root directory.
  • URL-decoding errors and malformed requests return 400 — they MUST NOT crash the process.
  • Uploads: size caps (media 600 MiB, templates 100 MiB), at most 2 concurrent transcodes, partial files deleted on abort, content type sniffed rather than trusted.

  • Template archives are extracted with zip-slip and zip-bomb protection (ratio and total-size caps).
  • Outbound requests the platform makes on a user's behalf (template install from URL, webhook delivery) MUST block private, loopback and link-local destinations unless the owner enables them, to prevent server-side request forgery.

7.12 Audit log

Append-only record of: logins (success and failure), session revocations, user and role changes, token creation and revocation, connection changes, template installs, overlay key rotations, exposure changes, backups and restores. Each entry: time, actor, IP, action, target. Retained 90 days by default. Never contains secrets.

7.13 Backups

POST /system/backup produces an archive of configuration, overlays, timelines, templates and media. Secrets inside stay encrypted with the master key; the export MAY additionally be wrapped with a user passphrase (scrypt-derived key, AES-256-GCM) for off-site storage. Restore requires owner role and the matching master key or passphrase.

9.2 The time rule

Times before the day boundary belong to the next calendar day. With date: 2026-08-28 and dayBoundary: "12:00", a slot at 01:00 is 2026-08-29 01:00 in the show's timezone — which is what a club night means. The boundary is configurable (an afternoon show sets it to "06:00").

All schedule times are converted once, server-side, to absolute instants using the show's timezone (IANA name). Clients receive instants; they never re-interpret wall-clock strings, so an operator's phone in another timezone shows correct countdowns.

9.4 Scheduler rules

  • The scheduler ticks at least once per second and fires every armed cue whose at has passed.
  • Grace window: a cue more than 5 minutes late is marked missed without firing. A wrong date or a restart after downtime never replays a night's worth of graphics at once.
  • Durable before visible: a cue's fired status is written to storage before its effect is published, so a crash can't fire it twice.
  • Timed scenes return server-side: a scene with durationMs + then (04 §4.2) schedules its return as part of the take, independent of any client.
  • Operator overrides — fire now, skip, re-arm — are always available and audited.
  • Editing the lineup regenerates generated cues (§9.5) while preserving the fired / skipped status of cues that still exist, so an edit mid-show doesn't re-fire what already happened.

9.5 Generated cues

A show MAY generate cues from its lineup with a recipe. The default recipe, per slot:

  • at slot start: show.slot + overlay.action: titleCard;
  • introOffsetMin after start (default 5): overlay.action: intro (the Event Intro);
  • every nowPlayingEveryMin (default 10) until the next slot: overlay.action: nowPlaying;
  • for the slot flagged headliner, at its start: overlay.action: headliner when the template provides it.

Recipes are data, not code, so a different kind of show (a talk show, a tournament) ships its own.

9.6 Planned shows

A show configuration MAY be saved against a future date. At the day boundary on that date the server activates it — lineup, settings, regenerated timeline — with no browser open. Plans more than 14 days past are pruned.

Hard rules & migration from v0

Each rule below was learned by something breaking during a live show or its rehearsal. They are normative: an implementation that violates one is not conformant, however well it does everything else.

Hard rules

H1 · Templates never connect. A template has no credentials and no route to a third party. Why: integration code spread across designs is unmaintainable and leaks tokens into a browser anyone can inspect. (04 §4.8)

H2 · Overlay URLs are permanent. Nothing configurable goes in an OBS URL — not the theme, the viewer-count mode, settings or the template version. Why: v0 put an event theme and a viewer flag in the URL; every toggle minted new links and sent the operator back into OBS to re-paste sources minutes before doors. (01 §1.4)

H3 · The server owns the show. Cues fire on the server. Why: v0 first ran its rundown in the browser; closing the laptop stopped the show. (09)

H4 · Durable before visible. Persist a cue's fired state before publishing its effect. Why: otherwise a crash between the two fires it again on restart. (09 §9.4)

H5 · No retroactive mass-fire. Cues more than 5 minutes late are marked missed, not fired. Why: a wrong date or a restart replayed an entire night of title cards at once. (09 §9.4)

H6 · Never show a wrong number. Unknown is hidden; errors hold the last good value briefly, then hide; only an authoritative report renders 0. Why: a failed API that renders "0 viewers" on stream is worse than showing nothing. (02 §2.8)

H7 · Times before the day boundary belong to the next day. Why: a Friday show with a 1:00 AM headliner must schedule him for Saturday 1:00 AM; every naive implementation puts him on Friday at 1 AM, before doors. (09 §9.2)

H8 · Headliner and closer are different. Why: v0 used "the CLOSER slot" as the headliner; on a bill where the closer wasn't the billed act, the event's Starting Soon card showed the wrong DJ. (09 §9.1)

H9 · Never gate correctness on requestAnimationFrame or animationend. Use timers and deadlines. Why: OBS stops frames to sources that aren't painting, background tabs throttle timers to about once a second, and animationend never fires on a hidden element — each of these froze v0 overlays at some point. (05 §5.2, §5.7)

H10 · Respect what a browser source can't see. backdrop-filter can't blur the camera; mix-blend-mode: multiply on a transparent page composites to black. Why: both shipped in v0 and blacked out or did nothing on air. (05 §5.8)

H11 · Nothing a client sends may crash the process. Why: v0 crashed about weekly because a scanner's malformed URL threw in decodeURIComponent outside any handler. (01 §1.7, 07 §7.11)

H12 · Transcode phone video. Why: iPhone .MOV is usually HEVC, which OBS's browser can't decode; the clip silently didn't play. Convert to H.264 MP4 and bake in rotation. (10 §10.2)

H13 · Phones get lite previews, loaded on tap. Why: two live overlay iframes with blur and grain exhausted iOS Safari's GPU memory and crash-looped the control page. (05 §5.8, 08 §8.3)

H14 · Beat OBS's cache. App files are no-store; template assets are versioned and immutable. Why: OBS kept serving stale overlay code after updates. (03 §3.4)

H15 · Setup lives on the server. Why: v0 kept the setup in browser storage; switching from the LAN address to the public one, or to a phone, showed an empty kit and the night's lineup had to be re-entered. (01 §1.2)

H16 · Concurrent edits are detected, not lost. ETags and If-Match on every mutable resource. Why: an initial page load pushed its stale copy over a newer server copy and erased an operator's work. (03 §3.1)

H17 · UI tolerates missing optional elements. Pages initialize defensively — a field moved to another page, or hidden by a template, never throws during startup. Why: moving one setting to the Settings page made the main page crash on load and render no links at all. (08)

H18 · Respect platform quotas as hard stops. On quota exhaustion, stop until reset. Why: retrying a YouTube quotaExceeded as if it were a rate limit has consumed whole days of quota in other streaming tools. (06 §6.7)

H19 · Test against the clock. Every scheduled behaviour is tested by setting it a few minutes ahead and watching it fire on a running server, not only by unit tests. Why: v0's time bugs (after-midnight, grace window, timezone) all passed reasoning and failed reality until tested this way.

H20 · Destructive actions are never one tap away. Reset, delete and key rotation sit behind a menu and a confirmation that names the consequence. Why: the v0 reset button sat in the phone toolbar next to navigation.
